#### Design Specificity Verdict

**Grounded, but with a generic dark-UI undertow.** The design earns specificity through the pipeline bar with per-stage tool icons, folder tiles with extension-colored gradient borders and wireframe corner handles, export versioning with target-based grouping, the Blender addon drag-to-install card, and bases library with cover images. However, the modal system, settings panels, toast notifications, toggle switches, and color palette picker are architecturally indistinguishable from any SaaS dashboard. The `confirm()` and `prompt()` calls are jarring OS-level breaks.

#### Cognitive Load Assessment

**Checklist: 3/8 passed**

- **FAIL** — 15+ interactive elements visible before project selection (titlebar 4 buttons, sidebar search + 5 chips, main 3 tabs + drop zone, panel 3 tabs)
- **PASS** — Information grouped by user goal (sidebar=selection, main=content, panel=metadata)
- **FAIL** — Progressive disclosure absent: all tools/stages always visible in Settings
- **PASS** — Max 3 levels of hierarchy
- **FAIL** — Chunking violated: 8 tools, 8 folder tiles, 5+ pipeline stages shown simultaneously
- **FAIL** — Navigation inconsistent: Back (bases), Close (gallery, settings), Cancel (new project) — four dismissal patterns
- **PASS** — Clear typographic hierarchy (22px → 15px → 12px → 10px → 9px)
- **FAIL** — Working memory demands: active project state lost between tabs, export targets must be recalled

**Working memory violations:**
- Export dialog requires remembering which files are already assigned
- Pipeline stage click skips stages with no confirmation
- Calendar day click silently sets release date with no project context shown

#### Emotional Journey

**What works:** First project creation modal is satisfying; pipeline green checkmark glow is rewarding; file drop sorting with glow feedback creates confidence.

**What's missing:** No cross-session progress signal; error states show raw exceptions; "All Done" is just green text; delete confirmation is inconsistent across features.

#### What's Working

1. **Pipeline bar as navigation + status** — immediately legible, domain-specific, dual purpose (status + control). Green glow on `.pcheck` is a well-crafted reward signal.

2. **Folder tile system with extension-colored borders** — `--fc` CSS variable driving gradient borders, glow effects, and icon colors creates cohesive visual language. Wireframe corner handles on hover reference 3D viewport selection UX.

3. **Export versioning system** — target-based grouping with collapse/expand, "CURRENT" badge, version numbering, and file pill assignment is domain-precise. Jump strip for 4+ targets is a smart overflow solution.

#### Priority Issues

### P0 — `confirm()` and `prompt()` in Production
**What:** `bases.js` uses `confirm()` for group deletion and `prompt()` for new group creation. OS-level modal dialogs that break the app's visual language.
**Why it matters:** Immersion-breaking. Cannot be styled. Inconsistent with the rest of the app's modal system.
**Fix:** Replace with the app's own modal system (`.ov-modal` + `.modal-box`).
**Suggested command:** `$impeccable polish`

### P1 — No Undo for Destructive Operations
**What:** Delete file, delete base file, delete tool, delete stage — all permanent with no undo buffer.
**Why it matters:** 3D artists deal with files that take hours to produce. Accidental deletion creates adoption-blocking anxiety.
**Fix:** Implement soft-delete with 5s undo window using existing toast infrastructure.
**Suggested command:** `$impeccable harden`

### P1 — Three Parallel Button Systems
**What:** `.btn-pri/.btn-sec`, `.btn-primary/.btn-secondary`, and `.bp/.bg` all define identical rules with slightly different properties. The new project modal in `index.html` still uses `.bp/.bg`.
**Why it matters:** Visual inconsistency across overlay surfaces. Maintenance burden.
**Fix:** Update `index.html` to use unified `.btn-primary/.btn-secondary` classes and remove redundant backward-compatible aliases.
**Suggested command:** `$impeccable polish`

### P2 — No In-App Help or Tooltips
**What:** Zero documentation, tooltips, or onboarding. First-time users see 8+ folders with no context.
**Why it matters:** New users cannot learn the app without external documentation.
**Fix:** Add contextual tooltips to pipeline stages, folder tiles, and the Blender addon card. Add a `?` help icon.
**Suggested command:** `$impeccable onboard`

### P2 — Toast Notification Race Condition
**What:** `showToast()` creates fixed-position elements with no stacking logic. Two toasts within 2s overlap.
**Why it matters:** Information loss when multiple operations fire rapidly.
**Fix:** Implement toast queue with vertical stacking.
**Suggested command:** `$impeccable polish`

#### Minor Observations

1. Font loading via Google Fonts CDN in a Tauri app creates flash of unstyled text on slow connections and breaks offline. Bundle locally.

2. Right panel at 285px is wider than the sidebar at 240px. For a metadata panel, consider 240px for both.

3. Z-index hierarchy is ad-hoc (200, 150, 800, 900). Establish a system (base=100, panel=200, modal=300, overlay=400).

4. Gallery calendar "set release" interaction is invisible — clicking a day cell sets the active project's release date with no indication which project.

5. The new project modal still uses `.bp`/`.bg` classes while all other modals use the unified system — missed during consolidation.

6. With 50+ projects, stagger animation creates 2s total cascade.

7. `thumbnail.js` base64 encoding loop will throw on files > ~16MB due to maximum call stack size from spread operator on subarray.

#### Questions to Consider

1. Why does the new project modal still use `.bp`/`.bg` while all other modals use the unified system?

2. The gallery calendar can set release dates, but nowhere in the main UI is a project's release date displayed. Is this intentional?

3. With 8 default tools and 5 default pipeline stages, how should onboarding adapt when a user's pipeline differs?

4. The Blender addon drag-install gives no feedback if the user drops outside Blender. Should there be a success/fail state?

5. If a user deletes a file from the project list, the file stays on disk. Is "Remove from Project" the correct label, or should this be clearer?

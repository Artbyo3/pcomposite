#### Design Specificity Verdict

**Verdict: Partially grounded — strong domain logic, generic visual shell.**

The *functional* design is deeply product-specific: the pipeline bar (Blender → Painter → Unity → Package → Upload), FBX versioning with target-based export cards, the bases library with Blender bridge integration, folder tiles auto-mapped to DCC tools, and checklist items tied to pipeline stages are all native to a 3D artist's workflow. No unrelated product could use this domain logic unchanged.

However, the *visual* design language — dark theme, accent color, gradient borders, card hover lifts, monospace labels, glow effects — is interchangeable with any modern dark-themed productivity tool (Linear, Raycast, Arc, etc.). The visual system doesn't communicate "3D art pipeline" beyond what the content labels say. There's no spatial metaphor, no 3D-aware visual element, no nods to the craft of compositing. The product character lives entirely in the data model, not in the design.

**Category-interchangeable choices:** The three-column layout, sidebar card list, pipeline stepper, gallery grid, and settings form could all belong to a project management tool, a code editor, or a video editor. The only truly anchored elements are the pipeline bar content and the folder tile icons.

**Missed opportunity:** The app manages 3D assets but has no spatial awareness in its UI — no thumbnails rendered in 3D context, no material previews, no aspect-ratio-aware image display (gallery thumbnails are forced to 1:1 squares regardless of image shape).

#### Emotional Journey

**What works emotionally:**
- Creating a project and auto-selecting it with a green toast feels rewarding and seamless
- Pipeline bar with green checkmarks delivers genuine progress satisfaction
- "ALL DONE" message at checklist completion is a proper peak moment
- Thumbnail images on project cards create visual pride ("my work looks good here")
- Gallery calendar provides a sense of timeline and release momentum

**What's missing:**
- **No first-run experience** — first impression is an empty state with no guidance
- **No project completion celebration** — pipeline reaches 100% with just a status change, no acknowledgment
- **Error anxiety** — raw exception text in toasts ("Error: Error: Os { code: 2, kind: NotFound...") is alarming
- **No undo for destructive actions** — deleting a file or base group creates anxiety about irreversible loss
- **No save indicator** — users don't know if their work is persisted
- **Native `prompt()`/`confirm()` breaks immersion** — jarring OS dialogs in a custom-themed app feel like bugs

#### What's Working

1. **The pipeline bar** is the strongest design element — a domain-specific progress metaphor that communicates 3D art workflow at a glance and supports direct manipulation. The green checkmark glow on completed stages provides genuine satisfaction.

2. **The bridge architecture** between PCOMPOSITE and Blender — auto-sorting dropped files by extension, passing context to the addon, tracking imported bases, and detecting renames across systems — is an impressive workflow integration that shows deep understanding of the 3D artist's file management pain.

3. **The bases library detail view** with its split layout (card preview with drag-drop cover on left, file list with drag-drop add on right) is well-composed and functionally grounded in how artists organize reference material.

#### Priority Issues

### P0 — Three Competing Modal Systems
**What:** modal.css, components.css, and settings.css each define their own overlay/modal/button systems with different border-radius, shadows, and animation approaches.
**Why it matters:** Visual inconsistency across the app's overlay surfaces. Subtly different UX feel between "New Project", "New Export", "Edit Tool", and "Settings" overlays.
**Fix:** Choose one system (components.css `.ov/.modal-box` is the most complete) and refactor modal.css and settings.css to use it. Remove all duplicate definitions.

### P1 — No Undo for Destructive Operations
**What:** `deleteFile()`, `removeBaseFile()`, `removeGroup()`, `deleteExport()` all destroy permanently. `deleteFile` has zero confirmation.
**Why it matters:** 3D artists deal with files that take hours to produce. Accidental deletion with no recovery path creates adoption-blocking anxiety.
**Fix:** Implement an undo-toast pattern: delete from the active view, show a toast with an "Undo" button for 5 seconds, then commit the deletion to disk after timeout.

### P1 — Button Style Proliferation
**What:** Eight distinct button class systems with different border-radius, font sizes, padding, and color treatments.
**Why it matters:** Buttons are the most common interactive element. Inconsistent appearance creates a persistent feeling that the UI is "off."
**Fix:** Create a single button component system: `.btn-primary`, `.btn-secondary`, `.btn-ghost`, `.btn-danger` with consistent sizing and states.

### P2 — Text Below 10px Minimum Readability
**What:** Labels at 7px, hints at 8px, metadata at 8-9px. Space Mono at 7px is near-illegible on non-retina displays.
**Why it matters:** Accessibility failure. On 1080p 15" screens, 7px renders at ~6.6 physical pixels.
**Fix:** Establish 10px minimum. Bump all 7px to 10px, 8px to 10-11px.

### P2 — No Loading/Save State Indicators
**What:** No visual feedback during async file operations. No "saving..." indicator. The app appears to freeze during I/O.
**Why it matters:** Users don't know if the app is working or broken. May double-click, navigate away, or force-quit.
**Fix:** Add a subtle loading indicator during async operations. Add a save indicator that appears briefly after saves.

- Color-only status indicators (pipeline dots, extension badges, stage labels)

#### Minor Observations

1. The `.pcard` `fadeUp` animation applies to all elements with class `.pcard`, which is also used in sidebar.css for project cards — would conflict if any other element uses this class.

2. The `--fc` custom property in files.css is set only via inline styles from JS with no CSS fallback. If JS fails to set it, folder tiles render with undefined colors.

3. Gallery forces 1:1 aspect ratio on all thumbnails regardless of original image proportions, potentially distorting wide or tall renders.

4. The theme system overrides CSS variables but leaves hardcoded colors untouched (`#ff6432` for app-card-status, specific hex values in constants.js).

5. `streamerMode` sanitizes display text but not file paths passed to `invoke('open_in_app')` — a potential privacy leak if Tauri events are logged.

6. Export version numbers auto-increment but can't be manually set, which could confuse artists who need to match a versioning scheme.

7. Toast positioning at `bottom:40px` can overlap with the status bar (28px) on different DPI scaling configurations.

8. The `selectProject` function directly mutates shared array elements — a fragile pattern.

9. The changelog card uses `position:fixed` which could overlap with context menus near the cursor.

10. The folder tile hover effect (translateY(-5px) + scale(1.02) + 24px shadow + radial glow) is dramatic for a productivity tool — consider a subtler elevation.

#### Questions to Consider

1. Why does the Bases library live in a full-screen overlay rather than a dedicated panel? It's a core workflow concept — should it be as accessible as Projects?

2. The export system requires manually typing a target name. Given that targets map 1:1 to bases, why not auto-generate export entries when a base is imported to a project?

3. The 3-column layout is fixed at 240px | auto | 285px. On a 1366px laptop screen, the main content area is ~841px. Should the right panel be collapsible?

4. Given the Blender bridge architecture, could the app show real-time connection status ("Blender connected" / "Blender not running")?

5. The gallery calendar and sidebar project list both serve browsing. Could they be unified?
